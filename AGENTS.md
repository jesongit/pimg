# Project instructions

## Online diagnostics

- The repository-root `online.env` contains the deployed instance URL (`URL`) and API bearer token (`TOKEN`). Read these values at runtime; do not copy their contents into source, documentation, logs, screenshots, shell arguments, or commits.
- `online.env` is local configuration and must remain ignored by Git. The Docker build context also excludes it through the existing allowlist in `.dockerignore`.
- Send the token in the HTTP header `Authorization: Bearer <TOKEN>`, never in the query string. Resolve API paths relative to `URL`.
- Start with read-only requests to `/api/diagnostics/status`, `/api/diagnostics/metrics`, `/api/diagnostics/logs`, and `/api/diagnostics/activity`. A diagnostics-scoped token cannot access `/api/admin/*`; respect that boundary and use the returned metrics/runtime logs to investigate page performance.
- Last verified on 2026-11-01: the supplied token could read diagnostic status/metrics/logs/telegram; administrator API requests returned 401. The deployed service reported v1.0.40. Recheck current state rather than assuming this version or permission remains unchanged.
- For TG connection problems, read `/api/diagnostics/telegram` on versions that include it. It passively reports the runtime/session-file state, actual TCP/proxy dial counters, recent safe failure types and proxy quota blocking. It never reconnects, tests providers, logs in, decrypts a session or exposes account IDs, phone numbers, API hashes, proxy addresses/passwords or paths. A 404 on an older deployment means the endpoint is unavailable; do not infer a TG failure from that response.
- TG diagnostic timestamps are Unix milliseconds. Distinguish the current `state`/`connection.transport_state` from historical `last_failure`; a past failure does not imply the recovered connection is still broken. TCP/proxy dial success without a ready event does not by itself locate the failure beyond the proxy or prove a password problem. Do not recommend deleting a session or reauthorizing solely because jobs say authorization is required.
- When the proxy is Mihomo, HTTP CONNECT 200 is sent before its upstream dial completes. `dial_successes` therefore counts accepted proxy requests, not verified Telegram reachability; proxy/node failures can surface later as MTProto EOF. Check Mihomo's upstream error before attributing EOF to a TG session or changing transport options. The local ignored `deploy/proxy/config.yaml` may help identify the intended setup, but its current deployment must be verified separately and its node credentials must never be printed.
- For slow page first reads, correlate the current process's metric details with Linux `process_disk_read_bytes`, `process_disk_write_bytes`, `process_io_read_chars`, `process_io_write_chars` and page-fault counters when available. Compare first and subsequent requests separately; a local warm-query benchmark is not production acceptance.
- `/api/admin/logs` serves both task and history queries. Match `QueryActivityTasks` versus `QueryUnifiedLogs` before comparing requests; a fast task poll is not evidence that a subsequent history read was fast. Filter retained metric details and samples by the current performance `instance_id`, because windows may span upgrades.
- Linux `write_bytes` is accounted when pages become dirty; deleted/truncated temporary files can cancel physical writeback. Treat the counter as process I/O accounting, not a disk-device write total. A process-wide delta also includes background media work and is not a per-request measurement.
- The tasks page is `/admin/tasks`; the logs page is `/admin/logs`. Verify their current API requests from the frontend source before measuring. With an administrator token, authenticated GET requests to those APIs are available as well.
- A request to diagnose online performance authorizes read-only investigation. Do not change online settings, start/cancel/retry jobs, clear history, restart the service, or deploy changes unless the user asks for those actions.
- Keep diagnostic evidence under the ignored `audit/` directory and redact credentials and private instance data from anything shared.

## Deployment

- `online.env` also records `SSH` (`user@host` of the deployed NAS). Key-based SSH works without a password; the instance URL and token share that file. Never print or commit those values.
- The deployed instance is a plain Docker container named `pimg` (no compose project): image `posase/pimg:<version>`, port `18787->8787`, restart policy `unless-stopped`, network `mihomo`, data mount `/vol2/1000/pimg -> /pimg/data`, a named volume at `/pimg/runtime`, and read-only media mounts under `/data/*`. Inspect the running container on the host and recreate it with the same mounts, ports, network and env; do not invent a compose file for it.
- Release flow: bump `Version` in `internal/server/server.go`, the OCI label in `Dockerfile`, add `docs/releases/vX.md`, and allowlist that file in `.gitignore`. Build and publish from the repo root with `docker buildx build --platform linux/amd64 -t posase/pimg:<version> -t posase/pimg:latest --push .`.
- The local Docker Desktop daemon is configured with manual proxy `http://127.0.0.1:7890` (Docker Hub is not reachable directly; that proxy is the local Clash mixed port). If the engine was restarted since, confirm proxy settings survived and `docker pull alpine:3.23` works before building.
- Updating the online container is pull-only: run `docker pull posase/pimg:<version>` on the SSH host, then recreate the `pimg` container with its existing configuration. Never transfer image tarballs (`docker save`/`load`, scp) or build from source on the host. After updating, verify `/api/diagnostics/status` reports the new version and `database_ok`.
